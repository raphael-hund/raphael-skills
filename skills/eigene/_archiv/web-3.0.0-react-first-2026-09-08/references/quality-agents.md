# MAKE Web Astra — orchestration and quality protocol

Read for major full-site delegation and independent review. This is a reusable protocol, not evidence of an already completed website. Contents: roles; dependencies/ownership; evidence; criticism; iteration; lean changes.

## One controller, twenty useful specialist agents

The lead is outside the twenty specialist roles. It owns scope, dispatch, integration, the dependency graph, shared acceptance records and authorised delivery. Compound Engineering supplies subordinate plan/work/review/learning phases; it must not launch a competing controller. Load one selected Taste implementation authority and route Impeccable operations by the actual problem.

When the user explicitly requests twenty agents for a major website build, dispatch twenty distinct useful specialist assignments when the host supports sub-agents. Otherwise use only the independent packages the task needs. A role becomes completed only when a real agent returns an inspected artifact or a specific evidence-backed finding. Merely printing this table does not satisfy twenty agents. Record actual agent IDs, assignments, model where exposed, paths, status and review results. No invented cross-model diversity or Astra-specific performance claims.

Discover the actual runtime limit before dispatch. For example, a host with seven total slots permits six active specialists beside the lead; discover the actual limit rather than assuming this example applies. Queue dependency-ready agents in waves and use completed slots; twenty specialists does not mean twenty simultaneous workers. Do not ask workers to spawn hidden secondary swarms. If a host lacks sub-agents, run the necessary specialist passes sequentially and explicitly report that independent-agent execution was unavailable.

## Dependencies, write ownership and handoff

1. **Discovery:** 01–05 establish facts, baseline, intent, visitor journeys and reference evidence. Start 06 and 07 once their specific inputs exist; they need not wait for unrelated research.
2. **Contracts:** reconcile art direction with search architecture, then let 08–10 establish real copy, assets, tokens and the design seed. The lead resolves conflicts before many pages repeat them. Start 11 and 16 where their dependencies are ready.
3. **Build:** 12–16 implement disjoint units. Reach one complete representative page for each actual archetype, have 17–20 review it, fix shared faults, then finish the remaining routes. This early checkpoint does not replace the required review of every final route.
4. **Independent review:** critics can inspect completed units while builders work elsewhere. Their findings are read-only. The lead routes accepted fixes to the responsible writer, then critics inspect the changed result.
5. **Reconcile and deliver:** 10 reconciles DESIGN.md against approved intent, actual code and rendered values. 19/20 verify deployed evidence when publishing is authorised. The lead captures only verified, reusable Compound lessons.

Maintain one write owner for every path at a time. The lead alone owns dependency installation, package manifests, lockfiles, shared configuration and integration bookkeeping unless explicitly delegated to one owner. Shared workspaces use nonoverlapping path leases; isolated worktrees may be used when supported. An agent cannot edit another owner's route to fix a convenient nearby issue. Record the required change and transfer ownership or wait. Critics never silently patch what they are judging. Workers do not commit/push or mutate a shared index unless specifically delegated and safe in the current workflow.

Each work order includes task ID, verified inputs, exact owned paths, dependencies, acceptance checks, out-of-scope boundaries and reviewer. Each handoff states changed files, evidence paths, unresolved findings, assumptions and integration needs. The lead inspects the actual diff or artifact, not only the agent's summary.

## Evidence that proves coverage

Create one route-level evidence index derived from the approved launch inventory. A page is not done because it appears in a sitemap, because its template passed, or because its builder likes it.

For **every launch route, including every SEO subpage**, independently inspect desktop and mobile screenshots at readable resolution. Record the viewport, browser, route/state, implementation snapshot, date, capture path and reviewer agent ID. Use a full-page overview for rhythm plus detailed crops where type, imagery or states cannot be judged. Complete lazy content loading and stabilise fonts before capture. A shared component screenshot does not substitute for checking the actual content and crops on each route.

Also cover representative intermediate widths per page family, the narrowest supported layout, long real copy, open navigation, form errors, visible focus, and reduced motion. Test all unique interaction types and every distinct destination. A shared form implementation can have one deep interaction test, but every occurrence must point to the intended endpoint and maintain valid context.

Every route requires separate machine-readable or command evidence for status, page identity, raw response HTML content, headings/landmarks, canonical, title/description, intended indexability and crawlable internal links. Verify complete live responses where metadata streams. Check sitemap/robots, unknown routes, removed URLs, redirects, asset loading and direct inner-page reloads on the actual host. Compare implemented routes with launch inventory to catch missing pages and orphan links. Schema must match visible, sourced content; validate what the available tool actually supports.

Record functional outcomes, not just clicks: menu destination reached; valid data accepted; invalid data rejected; failure state honest; confirmation tied to the real configured outcome. Production communications need existing user authorisation; use an isolated test destination where necessary and disclose any delivery not exercised. Do not claim end-to-end delivery from a mocked toast or HTTP 200 alone.

Measure production-build lab performance with tool version, route, build, device/network conditions and trace or report path. Investigate observed bottlenecks; repeat measurements only for noisy results or relevant fixes. Distinguish LCP/CLS lab observations and interaction diagnostics from field Core Web Vitals. Field data may be unavailable on a new site. Automated accessibility checks supplement keyboard, focus and visual inspection; zero detected issues is not a conformance certificate.

## Criticism that produces improvements

Before reviewing, give critics the approved brand, visitor task, search intent, supported constraints and real screenshots. Withhold builder self-praise and previous verdicts where practical. Independent agents using the same model provide a separate review pass; they do not establish model-family diversity.

Each finding must name route/state, screenshot or reproducible command, specific observed failure, user/brand impact, severity, proposed direction and verification condition. Distinguish:

- **Blocker:** missing agreed route, fabricated proof, broken primary action, accidental deindexing, inaccessible essential control, severe unreadability or unusable layout.
- **High:** a reproducible problem that substantially harms understanding, trust, brand identity, search-intent satisfaction or the primary journey.
- **Medium:** a material local flaw with a clear improvement and limited affected scope.
- **Low:** an optional preference or small polish opportunity; it cannot alone justify an endless loop.

Visual assessment covers brand specificity, hierarchy, type and wrapping, images/crops, layout rhythm, content clarity, density, responsive composition and interaction states. Critics must distinguish a deliberate design decision from a demonstrable flaw. Style rules from Taste/Impeccable are contextual inputs; they cannot remove useful SEO content, force an unrelated theme or override a brand-specific approved decision.

Select a small set of real comparable benchmark pages, identified in the reference ledger. Compare equivalent archetypes, purpose, viewport and section scope. Use matched side-by-side captures and anonymise order when practical. Record per criterion `weaker`, `comparable`, `stronger`, or `cannot assess`, with a visible reason. Do not claim scientific blindness when identities are evident, or conversion superiority without outcome data. An awards homepage is not evidence that a dense service page should discard explanatory content.

## Iteration, convergence and honest stopping

Work through the highest-impact open issue, not whatever is easiest to polish. Each cycle has a short accepted fix list, assigned owners, changed evidence, retest results and any rejected finding with a reason. After a shared-token/component fix, recheck affected route families; any affected previously approved captures become stale until recaptured. Keep rejection history so old images and discarded patterns do not return.

If the same substantial issue persists after repeated fixes, change the diagnosis: inspect actual font loading, dimensions, content, assets or architecture; compare a concrete alternative; escalate the relevant design decision. Do not impose a global cycle cap, and do not keep making tiny edits to an incorrect concept.

Completion requires all agreed launch routes built, independent mobile/desktop coverage current, critical functional and SEO evidence current, no unresolved blocker/high finding, and DESIGN.md reconciled. Medium findings must be fixed or explicitly justified as accepted limitations with owners; they cannot be silently downgraded. Finish when the remaining proposed edits lack a clear material benefit or would violate the approved direction. Nobody needs to say “wowed”, “perfect” or “AAA” for an evidence-backed conclusion.

Long work requests authorise substantial meaningful iteration; they do not justify fabricated elapsed time or waiting to satisfy a clock. Preserve checkpoints, carry the backlog through context limits, report actual limits honestly, and never claim a five-hour run that did not happen. If execution ends before the completion gate, mark the result incomplete with exact unfinished scope; do not redefine completion to match what happened to fit.

## Lean changes

For a typo, small spacing correction, one asset replacement, or similarly bounded reversible edit, retain the established stack and DESIGN.md. Inspect the affected context, make the focused change, check the relevant rendered state and update the contract only if the accepted system changed. Use the smallest applicable specialist/reviewer set. Do not generate a fresh twenty-agent programme, full-site SEO audit or new tests mirroring a one-line edit. User-explicit full review scope still takes precedence.
